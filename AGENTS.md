# Runbook for autonomous work on the US equity system

Authoritative for any agent working this project. Read in full before acting.
Nothing here is re-derivable from the code — it is what was learned the hard way.

## Where things are
- Backlog: `BACKLOG.md` in this directory. It is the tried-list: every registered
  candidate, its control, its numbers, and why it was kept or killed. The owner and daytime
  sessions curate it; the night lab cannot edit it.
- Night lab: `.github/workflows/night-lab.yml` runs an agent once a night under
  `research/NIGHT_AGENT.md`. It drives `research/lab.py` batches, writes only its own batch
  files and `research/NIGHT_LOG.md`, and registers any lead's forward test in that log for the
  owner to move into the backlog.
- Dashboard: `tracker.html`, regenerated by `dashboard.py`.
- Reports: daily and monthly summaries go to a private notes workspace. The routines that
  write them hold the page references in their own prompts; nothing in this repo needs them.
- Keep the working copy out of any cloud-synced folder. Sync stalls broke this project
  three separate times before it moved.

## What the system currently is
40 names, equal weight, rebalanced monthly, capped 8 per sector.
Ranked on **value only**: sales-to-price, book-to-market, cash-flow-to-price.
Measured 2024-09..2026-07, 23 chained months: book +37.0%/yr vs SPY +16.5%, t=1.68.

## Five findings that must not be re-litigated
1. **Screen on the real objective.** Rank signals by how a 40-name long-only book
   performs against SPY — NOT by quintile spread. Spread rewards a signal whose
   bottom decile is terrible, which is meaningless when you cannot short. Every
   screen before 2026-09-22 used spread and promoted signals that measured
   -4.91% and -5.30% on the objective they were meant to serve.
2. **The screen certifies 10% of pure noise.** Measured, not assumed: 200 random
   signals through the four-test screen, 21 passed. Any single "discovery" is more
   likely luck than signal. `research/screen_on_objective.py` holds the null.
3. **Two-source rule.** Nothing enters the book without BOTH published evidence
   (an OSAP survivor or equivalent) AND our own data. Signals with only one leg
   have failed repeatedly.
4. **Survivorship is NOT the problem.** Measured at 0.27%/quarter attrition, a drag
   of at most 0.27pp. It was the leading hypothesis for the implausible edge and
   it is wrong. Do not re-run this.
5. **The measured edge is ~4x the documented value premium.** +20.6pp/yr against a
   published 4-5pp. Treat the excess as selection bias until forward evidence says
   otherwise. Plan for 4-5pp.

## How fundamentals.parquet is built, and why it must not be shortcut
`data/sec/fundamentals.parquet` is NOT built from the XBRL frames API alone. Frames
return only `accn, cik, entityName, loc, start, end, val` — no `form`, no filing date.
The real chain is three scripts, in order:

1. `recorder/fetch_frames.py`       — caches frames responses into `data/sec/frames/`
2. `recorder/fetch_filing_index.py` — builds `data/sec/accn_index.parquet` (accn -> form,
                                      real filed_date) from EDGAR quarterly `master.idx`
3. `recorder/build_fundamentals.py` — joins 1 and 2, then joins tickers on padded CIK

Skipping step 2 breaks two things silently, and on 2026-10-06 a rewrite of
`research/bootstrap_all.py` did exactly that:
- **`form` is null on every row**, so the domestic-filer filter in `signals/build_all.py`
  resolves to an EMPTY universe. That filter is what caught Fannie Mae preferred at
  $36,480bn (preferred lines inheriting the parent's share count) and ADR mismatches.
- **`filed_date` has to be guessed.** The bad version used `period_end + 45 days`, which
  is lookahead for every filer that reports slower than 45 days — most smaller ones.
  The entire point-in-time guarantee the research rests on runs through this column.

The frames fetch must cover **annual** frames (`CY2024`) as well as quarterly
(`CY2024Q1`). `build_all.py` selects on `dur.between(60, 115)`, so the live book is
quarterly-only and does not need them — but `build_valprof.py` (FY revenue, FY operating
cash flow), `build_payout.py`, `build_events.py`, `pit_growth.py`, `pit_distress.py` and
`pit_redflags.py` all filter on `fp == "FY"` or a duration near 365. Fetching quarterly
alone left the Mac with 246,666 annual rows the cloud did not have: the live book matched,
and every one of those scripts would have silently computed on an empty frame.

Both now fail loud: `build_all.py` refuses to score if fewer than 1,000 domestic filers
resolve, `build_fundamentals.py` exits if the accession index is missing, and
`bootstrap_all.py` validates a cached copy rather than trusting that it exists. Do not
weaken these into warnings — this failure mode is invisible from the outside, which is
the same way the recorder failed five times.

## The cloud price panel must be deep, not just present
`data/prices/history_3y.parquet` lives in the Actions cache. The first cloud bootstrap
(2026-10-06) pulled 3y history only for the latest weekday snapshot's ~4,900 tickers;
the panel "existed", and `orders.py` silently skipped top-ranked names it could not
price, so the cloud book differed from the Mac's by five names. `bootstrap_prices.py`
now requires 7,000+ tickers with 500+ days and otherwise reseeds from the `panel-seed`
GitHub release (the Mac's panel, 10,207 tickers). Do not re-pull from Yahoo instead:
delisted names are purged there and cannot be recovered. If the seed ever needs
refreshing, upload the Mac's panel to that release — never a cloud-built one.

## Hard limits on autonomous action
- **Never change the live book.** Promotion requires two-source evidence AND
  forward confirmation at a threshold registered BEFORE the data existed.
- **Never invent or adjust a threshold after seeing data.**
- **Never place a trade or touch money.** Nothing is invested; this is research.
- Refuted hypotheses stay visible in the backlog as findings, not deletions.

## Daily plumbing (automated on GitHub Actions, `.github/workflows/daily.yml`)
Tue-Sat: snapshot -> refresh prices -> build signals -> rank -> orders -> score ->
dashboard.py, committed back to this repo, then `recorder/sanity.py` checks the rebuilt book.
The derived-data cache is restored only by the exact key in `data/derived_cache_key.txt`,
which each run commits; never go back to a prefix match, which would trust a cache any job
in the repo could have saved. An agent's job is to notice when that
plumbing lies, not to repeat it.

## What an agent should actually add
The cron pipeline cannot: republish the artifact, read the scoreboard and judge it,
decide what to research next, or notice that something passed while being wrong.
That is the work.
